# ADR 011: Transactional synthetic registry and version-pinned references

Date: 2026-10-22

Status: **Accepted — isolated synthetic development slice; production authority and schema sign-off remain unapproved**

## Context and decision

P0 validated payload shape but did not ensure JSON UUID fields referred to existing records of the correct kind. Implement a single PostgreSQL transaction for ten unverified draft kinds: industry, technology, company, instrument, document, source, event, claim, evidence and relationship. Protected and later-phase kinds remain denied.

`SyntheticRegistry.put` validates an explicit dummy principal, synthetic provenance/rights, expected version and all reference targets before committing the immutable payload, pinned reference rows, database-only commit record, operation and audit event. Actor-scoped idempotency keys bind the complete normalized request; conflicting payloads fail. Advisory transaction locks serialize first creation, while expected-version comparison prevents stale updates. Failed writes roll back their operation reservation and can be retried. Failed/denied attempts do not yet have a durable independent audit channel.

References pin the target version resolved at write time. Repeated references to one target within a request reuse one snapshot. Historical payloads and reference rows do not change when a target receives a new revision. This is per-target snapshot consistency under PostgreSQL READ COMMITTED, not a globally simultaneous multi-entity snapshot or a semantic cycle detector. Classification cannot be downgraded through revisions or references. Currently the only permitted license/use pair is `synthetic-only` / `local_research`; this is not a general license engine.

Document content identity (digest, size, media type), source original document and instrument issuer/class identity cannot change under an existing ID. Claim subject must match event company. Evidence document identity/digest must match its source. An issuer edge must match security master; a source support/contradiction edge requires matching evidence. Other proposed relationship predicates are typed draft links, not verified economic assertions.

## Canonical encoding

`ios-json-v1` is a project-specific UTF-8 JSON encoding, not RFC 8785/JCS: sorted string object keys, compact separators, Unicode preserved, array order preserved; aware datetimes become UTC with six fractional digits and `Z`; finite Decimal values become exact normalized decimal strings without rounding; UUIDs/enums become strings. Naive datetimes, non-finite values and non-string keys fail. Strings, source bytes and newlines are never silently normalized. Cross-language implementations need shared fixtures before compatibility is claimed. A future encoding version requires an explicit migration, never reinterpretation of existing hashes.

Hashes cover both the normalized payload and the sorted `(field, target UUID, target version)` projection. Readback checks the stored JSONB and reference projection against immutable commit digests. New SQL triggers prevent entity kind changes, payload-kind/schema mismatch and updates/deletes of references/commit records. Direct SQL from the trusted schema owner can bypass application checks or insert new rows; these hashes detect accidental alteration, not a malicious database administrator. The API remains SELECT-only, with no registry write endpoint. The development library uses a public dummy owner connection, not a production least-privilege writer.

## Compatibility and boundaries

Migration `0002_registry` adds commit records and guards without rewriting P0 payloads. Raw P0 rows have no registry seal and are rejected by this reader; adoption requires a separately reviewed reconciliation that validates references and preserves history. No legacy ledger is created, reset or copied.

A registry commit proves one database transaction. It is distinct from the existing future Vault `Receipt` contract and never claims document byte capture, physical Vault write, Obsidian index completion, device sync or external delivery. The repeatable demo uses metadata fixtures, not original documents. Real intake, authorization, protected approval and cross-store journaling remain later P1/P2 work.

## Validation

Real PostgreSQL tests cover replay, concurrent creation/update, wrong/missing references, classification, semantic links, protected writes, injected audit failure and tampered reference detection. The restore drill compares all seven registry transaction tables after actual pg_dump/pg_restore and exercises migration down/up in its temporary restored database. See ../P1_REGISTRY_STATUS.md for observed commands/results.
